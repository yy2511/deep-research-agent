# DeepSearchQA 全量 900 题实验报告：系统运行表现

> 本文分析 2026-10-11 至 10-13 跑完的 DeepSearchQA 全量评测中，系统在耗时、模型调用、token、缓存命中、工具调用、子 Agent 等方面的表现。答题质量的归因（非满分题分类）见 [评测迭代总结](评测迭代总结.md)。
>
> 统计脚本放在会话临时目录，没有进仓库：`perf_extract.py` 逐题抽取，`perf_agg.py` 汇总。数据来自各题的 `result.json`、`llm_usage.jsonl` 和 `runs/<run_id>/tool_calls.jsonl`。

## 三、耗时

### 3.1 分布

每题耗时（从开始到交稿）：

| 平均 | 中位数 | 90 分位 | 99 分位 | 最短 | 最长 |
|---|---|---|---|---|---|
| 807 s | 626 s | 1679 s | 2418 s | 83 s | 8167 s |

- 一半的题 10 分钟左右做完，九成在 28 分钟内做完。
- 16 题超过 2400 秒，其中 13 题就是没答案的题。另外 3 道没答案的题来自批次 A，那时的时限是 1200 秒。
- 有 2 题超过 2700 秒：798 用了 8167 秒，399 用了 7229 秒。原因是存证时"摘录近似匹配"卡死，时限打断不了，已经改用 Myers 算法修掉。

### 3.2 耗时越长，分数越低

| 耗时区间 | 题数 | F1 | 满分率 |
|---|---|---|---|
| < 5 分钟 | 156 | 97.8% | 92.3% |
| 5–10 分钟 | 245 | 95.1% | 90.6% |
| 10–20 分钟 | 280 | 95.2% | 88.6% |
| 20–40 分钟 | 153 | 84.7% | 72.5% |
| ≥ 40 分钟（超时） | 16 | 12.5% | 12.5% |

这主要是因为难题本来就慢，不能理解成"跑得越久越差"。20 分钟以上的题是丢分的主要来源。

### 3.3 时间花在哪里

按主 Agent 这条主线看（只统计没超时的题）：

- **约 70% 的时间在等模型回复。** 主 Agent 的模型调用耗时之和除以总耗时，中位数是 71%。
- **约 14% 在等工具。** 同一轮里并行的工具只按最慢的那个算，中位数是 14%。
- **剩下约 15%** 是重试等待、子 Agent 收发等其他开销。

**结论：** 速度瓶颈在模型服务，不在搜索或抓取。所以白天 ITKK 首字慢的时候，整体就会明显变慢。

## 四、模型调用与 token（827 题）

### 4.1 总量

| 项 | 合计 | 每题平均 | 每题中位数 | 每题 90 分位 |
|---|---|---|---|---|
| 成功的模型调用 | 28,670 次 | 35 | 28 | 70 |
| 输入 token | 13.6 亿 | 165 万 | 113 万 | 390 万 |
| 其中没命中缓存的 | 2.3 亿 | 28 万 | 16 万 | 58 万 |
| 输出 token | 3359 万 | 4.1 万 | 3.2 万 | 8.1 万 |

- **输入远大于输出，比例约 40 : 1。** 这是 Agent 循环的特点：每一轮都要带上前面所有的对话和工具结果。
- 最多的一题用了 1388 万输入 token、160 次调用。

### 4.2 按角色分

| 角色 | 调用次数 | 输入 token | 输出 token | 缓存命中率 |
|---|---|---|---|---|
| 主 Agent（lead） | 18,625 | 9.70 亿 | 2336 万 | 87.7% |
| 子 Agent（subagent） | 8,998 | 3.76 亿 | 770 万 | 83.7% |
| 研究计划（research_brief） | 834 | 144 万 | 162 万 | 4.2% |
| 上下文压缩（condense） | 213 | 1387 万 | 91 万 | 0.2% |

- 主 Agent 每题平均 23 次调用，中位数 20 次。
- 有子 Agent 的题，子 Agent 每题平均 28 次调用。
- 压缩一共只触发 213 次，占比很小。

### 4.3 思考 token：两家服务商报的数不可比

- opencode 报的思考 token 约占输出的 60%。
- ITKK 只报约 7%，483 题全题思考 token 不到 2000。

同一模型、同一 effort，不应该差这么多。更可能是 ITKK 流式返回时没有如实报思考 token。所以**本报告不用思考 token 做任何结论**。

## 五、缓存命中

| 范围 | 命中率 |
|---|---|
| 全部（有命中数据的输入占 96.9%） | **85.6%** |
| 主 Agent | 87.7% |
| 子 Agent | 83.7% |
| ITKK | 85.8% |
| opencode | 85.0% |
| 研究计划、压缩 | 0–4% |

- **主循环缓存命中很好。** 每轮请求的前面部分（系统提示、工具定义、之前的对话）基本不变，服务商的前缀缓存能直接复用。每题 165 万输入里只有约 28 万要按全价算。
- **研究计划和压缩几乎不命中。** 它们是一次性请求，每次内容都不同，这是正常的。不过它们的量很小（合计约 1500 万输入），不影响整体。
- **两家服务商的命中率几乎一样。** 说明命中率主要由我们的请求结构决定，跟走哪家关系不大。
- ITKK 有约 3% 的请求没报缓存数据，按"未知"处理，没有算进命中率。

## 六、服务商对比：ITKK vs opencode

两家跑的是同一模型、同一配置。

| 指标 | ITKK（681 题） | opencode（146 题） |
|---|---|---|
| 首字延迟中位数 | 9.8 s | **4.7 s** |
| 首字延迟 90 分位 | 34.0 s | **13.3 s** |
| 首字延迟 99 分位 | 90.0 s | 40.0 s |
| 单次调用耗时中位数 | 16.2 s | **11.7 s** |
| 单次调用耗时 90 分位 | 47.4 s | **30.7 s** |
| 请求失败率（含之后重试成功的） | 3.65% | 2.24% |
| 每题耗时中位数 | 685 s | **546 s** |
| F1 | 92.4% | 91.8% |

- **opencode 明显更快。** 首字延迟中位数约是 ITKK 的一半，长尾也短很多。分数基本一样。
- **ITKK 的失败主要是连接错误。** 共 476 次连接错误、183 次 500、92 次超时。
- 失败的请求都会重试。没答案的 16 题，停止原因都记为"到时限"，没有一题是因为请求失败直接中止的。不过重试会占用时间，对超时有多大贡献没有单独统计。

### 7.2 失败原因

**read_source 失败 2,581 次。** 前两类原因：

- **1,877 次是"取正文失败：未知错误（HTTPError）"。** 这是最值得注意的一项：
  - **只在 10-12 13:00 以后出现。** 之前的批次 A（1,427 次读原文）一次都没有。之后各批都有，约占读原文的 12–14%。高的时段（如 17:00）达到 25%。
  - **失败得很快。** 中位数 0.27 秒，不像是目标网站慢。同一来源之后重读成功的只有 37 次。
  - **推测是正文提取服务（Tavily extract）那边拒绝了请求**，比如额度、限流或某个 key 出了问题。但我们的错误信息只保留异常类名、不保留状态码（为了不泄露密钥），现在**确定不了具体原因**。
- **559 次是"原文中找不到该子串"。** 模型按关键词定位时没对上原文，属于正常的试错，它会换个片段再试。

**download_source 失败 27.3%。** 主要原因：

- 340 次是对方返回 HTTP 错误码（403/404 之类）。
- 239 次超时。
- 182 次是 SSL 错误。

这些大多是目标网站拦截或证书问题，属于外部原因。

**bash 失败 8.5%。** 主要原因：

- 388 次是命令超过 30 秒默认时限。模型可以自己把时限调到最高 120 秒。
- 176 次是程序报错退出。

**save_evidence 失败 4.0%。** 主要是摘录在已读原文里对不上，系统要求先补读原文再存证。这是有意为之的证据校验。

**finish_research 被拒 152 次。** 原因：

- 118 次是"还有未读消息或子任务没结束"。
- 34 次是草稿引用了不存在的卡片编号。

两类都是交稿前的校验，模型改正后都能重新交稿。

## 十、主要发现

1. **模型服务的速度决定整体速度。** 70% 的时间在等模型。opencode 的首字延迟约是 ITKK 的一半，每题耗时少约 20%。要提速，先选更快、更稳的服务商，再考虑改流程。
2. **缓存命中率约 86%，成本大头已经被缓存压下来。** 每题平均 165 万输入 token，其中只有约 28 万要按全价算。
3. **正文提取在 10-12 下午之后约有 12% 的请求快速失败（HTTPError），原因还不清楚。** 这会让模型少读到一部分原文，可能影响一部分题的分数。建议：
   - 错误信息里保留 HTTP 状态码（不涉及密钥）；
   - 核对那个时段 Tavily key 的额度和限流。
4. **长尾在时限上。** 超过 20 分钟的题 F1 只有 85%。16 道没答案的题在之后补跑时，用"预留 5 分钟交稿"全部交出了答案。另有 2 题因存证匹配卡死远超时限，已经修复。
5. **校验机制在正常工作。** 存证对不上原文、交稿引用了不存在的卡片，都会被拒绝并让模型改正。这些拒绝没有导致失败。

## 十一、口径说明与没验证的部分

- **没算钱。** 两家服务商都没有回传可信的单次费用（ITKK 回的是占位值），所以只报 token 量，没有换算成金额。
- **思考 token 两家报的口径不同，不可比。** 见 4.3。
- **批次之间不是严格对照。** 时间段、服务商、并发都不同，题目也不同，批次间的分数差异不能直接归因。ITKK 和 opencode 的速度对比是按调用统计的，比较可靠；分数对比只能作为参考。
- **耗时拆分是近似值。** 主 Agent 的工具时间按"每轮最慢的那个工具"估算，没有算子 Agent 的并行时间。
- **HTTPError 的原因没有查实。** 只能从时间分布和失败速度推测是提取服务那边的问题。
- **缺失的数据：**
  - 批次 A 前 23 题没有模型用量记录。
  - 10-08 的 hard50 正式版没有用量记录，所以第九节用的是重跑版。
