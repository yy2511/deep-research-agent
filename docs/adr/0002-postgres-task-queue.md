# 0002：PostgreSQL 存业务数据，任务表兼作队列，不引入 Kafka

- 状态：已接受
- 日期：2026-11-05

## 背景

现在研究在 Web 进程的后台线程里跑，进度存在内存，服务重启即中断；运行记录是本地文件，无法按用户查询。研究任务的特点是数量少、单个耗时长（分钟级）。线上机器内存 1.9G。

## 决定

- 用户、会话、任务、执行记录、额度、用量等结构化数据存 PostgreSQL。
- 待执行任务就是任务表里的记录；多个 Worker 用短事务 `SELECT ... FOR UPDATE SKIP LOCKED` 领取，研究在事务外执行。
- 来源快照、报告、附件等大文件继续放文件存储，数据库只存位置和哈希。
- Redis 只在有具体用途时引入（限流、搜索缓存、进度通知），由单独的 ADR 记录。

## 考虑过的其他选择

- Kafka / RabbitMQ：为高吞吐设计，这里任务量很小；多一个组件要维护，还要处理“数据库状态和队列消息不一致”的问题。
- Redis 队列：可行，但任务状态会分在数据库和 Redis 两处。
- MySQL：同样支持 `SKIP LOCKED`；选 PostgreSQL 是因为它自带 `LISTEN/NOTIFY` 可用于进度通知，且在 Python 生态更常见。索引、事务、锁等概念两者相通。

## 代价与影响

- 领取任务依赖数据库，数据库不可用时无法开始新研究。
- 单次研究的事件可达数万条，写入事件时需要批量提交或只把索引入库，具体方案在实现时定。
- 线上内存紧张，部署前需评估 PostgreSQL 占用，必要时升级机器或使用托管数据库。
