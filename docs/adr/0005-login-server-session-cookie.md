# 0005：登录用服务端会话 + HttpOnly Cookie，不用 JWT

- 状态：草稿
- 日期：2026-11-06
- 作者：Claude Code
- 关联：#25、[阶段1-数据库与用户](../design/阶段1-数据库与用户.md)、[后端扩展总体方案 §6.1](../design/后端扩展总体方案.md#61-登录与权限)

## 背景

现在没有账号，线上靠 Caddy `basic_auth` 一个共用密码（`deploy/Caddyfile.dra`）。第 1 阶段要让每个人用自己的邮箱和密码登录，之后每次请求都要知道“这是谁”。

约束：

- 前端和接口同域：生产时前端构建产物由 FastAPI 挂在 `/`（`src/dra/api/app.py`），开发时 Vite 把 `/api` 代理到后端（`web/vite.config.ts`），浏览器看来都是同一个站点。
- 有不少请求不是前端 `fetch` 发的，**无法自己加请求头**：
  - 研究进度用 `EventSource`（`web/src/api.ts` `openStream`）；
  - 图片 `<img src="/api/runs/.../images/...">`（`ConversationWorkspace.tsx`）；
  - 原件、资料、附件的链接和 `<iframe>` 预览（`DocumentLink.tsx`、`LibraryPanel.tsx`、`ArtifactFiles.tsx`）。
- 只有一个后端服务，没有第三方客户端或跨域调用。
- 内测期间需要能让某个人立即下线（停用账号、怀疑密码泄露）。

## 评估标准

1. 上面那些不能加请求头的请求能不能带上身份。
2. 能不能立即让某个会话失效。
3. 页面被注入脚本时，登录凭证会不会被偷走。
4. 实现和维护量；学习价值。

## 候选方案

| 标准 | A. 服务端会话 + HttpOnly Cookie | B. JWT 放请求头（Bearer） | C. JWT 放 Cookie | 维持现状（Caddy 共用密码） |
| --- | --- | --- | --- | --- |
| 不能加头的请求 | 浏览器自动带 Cookie，全部可用 | `EventSource`、`<img>`、链接都带不上，要把令牌放进 URL（会进日志和浏览器历史） | 自动带 | 自动带 |
| 立即失效 | 删掉或标记数据库里的会话记录即可 | 令牌到期前一直有效；要立即失效得另建黑名单，等于又回到查库 | 同 B | 只能改全站密码 |
| 被注入脚本时 | HttpOnly，脚本读不到 | 令牌存在 `localStorage`，脚本能读走 | HttpOnly 时读不到 | 浏览器保存，脚本读不到 |
| 实现量 | 一张 `sessions` 表 + 每次请求查一次库 | 签名密钥管理、续期逻辑、前端每处请求加头 | 签名 + Cookie + 黑名单 | 无 |
| 区分用户 | 能 | 能 | 能 | 不能，无法满足第 1 阶段目标 |

## 决定

选 A。

- 登录成功后生成 32 字节随机令牌放进 Cookie；数据库 `sessions` 表只存令牌的 SHA-256 哈希。数据库泄露也拿不到可用的令牌。
- Cookie 属性：`HttpOnly`、`SameSite=Lax`、`Path=/`；经 HTTPS 访问时加 `Secure`。
- 每个请求由一个 FastAPI 依赖读 Cookie、查会话、得到当前用户，接口里通过 `Depends` 取用，方式同 #18 的存储注入。
- 登出、停用账号、管理员重置密码时，把相关会话标为已吊销，立即生效。
- 跨站请求伪造（CSRF）：`SameSite=Lax` 使别的网站发起的 POST/PUT/DELETE 不带这个 Cookie；另外对这类请求检查 `Origin` 头必须是本站。

具体参数（有效期、续期方式）见[设计文档](../design/阶段1-数据库与用户.md)。

## 代价

- 每个请求多一次数据库查询（按令牌哈希的唯一索引查一行）。内测规模下可以忽略；以后真成为瓶颈，再加缓存（第 4 阶段 Redis 可顺带承担）。
- 会话存在数据库里，数据库不可用时所有人都无法使用（这一点与 ADR 0002 一致：数据库本来就是必需的）。
- Cookie 绑定在本站域名下，以后要支持其他域名的客户端（手机 App、第三方调用）时，需要另加一种凭证。

## 何时重新评估

- 需要给另一个域名的前端、手机 App 或第三方程序开放接口。
- 拆成多个独立部署的后端服务，彼此需要传递用户身份。
- 会话查询在监控里成为明显的延迟来源。
