# 管理后台邀请链接

- 状态：草稿，待评审
- 日期：2026-11-19
- 作者：Codex
- 关联：[功能 #75](https://github.com/yy2511/deep-research-agent/issues/75)、[阶段 1 账号与登录](阶段1-数据库与用户.md)、[ADR 0009](../adr/0009-platform-roles-and-user-quotas.md)

## 目标与范围

平台负责人在「用户管理」生成并复制一条邀请链接。受邀人打开链接进入注册表单，只填写邮箱、密码和确认密码。注册成功后自动登录为普通用户。链接用于一次成功注册，发给多人共用同一码的需求由 [#59](https://github.com/yy2511/deep-research-agent/issues/59) 跟踪。

## 现状

- [管理命令的 `_create_invite`](../../src/dra/admin.py) 调用 [`auth.create_invite`](../../src/dra/api/services/auth.py)，生成时返回明文及到期时间。[Invite](../../src/dra/db_tables.py) 已存哈希、失效时间、发放人与使用记录。
- [`api_register`](../../src/dra/api/routers/auth.py) 接收邀请码、邮箱和密码。服务在同一事务中创建账号、标记邀请码已用并建立登录会话。[AuthGate](../../web/src/components/AuthGate.tsx) 在未登录时可先显示公开示例，现有注册表单由登录页手动切入。
- [用户管理 PR #67](https://github.com/yy2511/deep-research-agent/pull/67) 提供管理页和负责人角色，其 `auth.register` 为邀请码注册的用户写入不限次额度。已合并的 [角色设计 PR #65](https://github.com/yy2511/deep-research-agent/pull/65) 规定只有负责人能授予不限次额度。

## 方案

评估标准是发放时可在网页内完成、受邀人直接进入现有注册流程，以及发放权限与注册结果相符。

| 选项 | 结果 |
| --- | --- |
| 维持命令行生成、手动填码 | 沿用现有链路，两端仍需手动操作 |
| 网页生成独立的邀请凭据和注册流程 | 可实现相同体验，需要维护另一套有效期、使用状态和注册规则 |
| 网页发放现有邀请码，链接带码打开现有注册表单（选定） | 复用现有事务和失效行为，新增发放入口及链接解析 |

### 管理入口和权限

以 [#67](https://github.com/yy2511/deep-research-agent/pull/67) 合并后的「平台管理 → 用户管理」为实现基线。在页面上方给平台负责人（`owner`）显示「生成邀请链接」。新账号沿用邀请码注册的不限次普通用户策略，因此发放权限沿用 ADR 0009 的负责人权限。页面使用当前账号角色显示入口，后端独立检查当前有效会话及负责人角色。

点击后发起一次创建请求，等待期间按钮显示生成中。成功后显示可选中的只读链接、服务端返回的到期时间和「复制链接」按钮。生成成功的响应提供明文，页面只在当前生成结果中展示该链接。

### 发放接口

新增 `POST /api/admin/invites`，使用现有会话与同源检查。请求 JSON 为 `{}`，第一版页面用服务端默认有效期。服务调用 `auth.create_invite(db, created_by=issuer.id)`，复用 `invites` 表并记录负责人账号 ID。命令行继续按现有参数调用同一服务。

成功返回 `201` 和 `Cache-Control: no-store`。以下为合成响应示例。

```json
{
  "invite_code": "EXAMPLE-INVITE-CODE",
  "expires_at": "2026-12-03T04:00:00Z"
}
```

未登录或会话失效返回 `401`。平台管理员（`admin`）、普通用户和访客调用返回 `403`。响应错误文本沿用现有接口格式。

### 链接与注册

前端用当前站点 origin 拼出 `/#invite=<编码后的邀请码>` 的绝对地址。将码放在 URL 片段中，浏览器打开页面时只把站点路径发给服务器，邀请码由注册表单提交给后端。

`AuthGate` 对带码链接优先展示注册表单，即使站点有公开示例也直接进入注册。表单自动带入邀请码，邮箱、密码和确认密码由受邀人填写。链接打开时只展示表单。提交仍走 `POST /api/auth/register`，服务端沿用已有的邀请码校验、账号创建和登录事务。注册成功后清除地址栏里的邀请片段。手动填码入口继续使用同一注册表单。

已有登录会话时沿用工作台的登录态，用户主动退出后可用同一个链接注册新账号。

## 失败、重试与并发

- 发放请求失败时沿用接口的中文错误提示，用户可重新点击生成。
- 邮箱已注册、密码不符合要求时沿用注册页提示。邀请码仍有效时可更正表单后重试。
- 已用、过期或无效的码沿用「邀请码无效或已使用」。两人同时提交同一个码时，由现有条件更新保证只有一人成功。

## 验收场景

| 场景 | 预期 |
| --- | --- |
| 负责人发放邀请 | 页面能复制链接并显示到期时间。库中保存哈希和发放人 ID |
| 其他角色或匿名直接请求发放接口 | `admin`、`user`、`guest` 为 `403`，匿名为 `401`，邀请记录数量保持原样 |
| 在未登录窗口打开链接，站点有公开示例 | 直接显示预填好的注册表单 |
| 打开或刷新链接、更正重复邮箱后再提交 | 成功提交前码保持可用 |
| 提交有效码 | 创建不限次普通用户并直接登录，随后该码再次提交被拒 |
| 提交过期码 | 显示现有错误提示 |
| 使用旧命令或手动填码入口 | 原有生成和注册测试通过 |

后端在临时测试数据库验证发放权限、存储及注册。前端覆盖生成、复制、链接打开、有示例的注册入口与普通登录回归。实现 PR 记录实际测试结果。

## 影响的限制

网页入口沿用当前的默认 14 天、成功注册一次、邮箱唯一性和密码要求。首次生成时返回明文。网页发放不限次用户的邀请遵循现有的负责人权限。命令行仍可用现有参数指定有效期和备注。
