# 阶段 1：数据库与用户

- 状态：已接受
- 日期：2026-11-06
- 作者：Claude Code
- 关联：#25；[ADR 0002](../adr/0002-postgres-task-queue.md)、[0005](../adr/0005-login-server-session-cookie.md)、[0006](../adr/0006-sqlalchemy-alembic-sync.md)；上级设计 [后端扩展总体方案](后端扩展总体方案.md) §4–§7

## 目标与不做什么

做完后用户能感受到：

- 新用户凭邀请码注册，之后用邮箱和密码登录。
- 每个人只看得到自己的研究、对话和资料库。
- 只有管理员能改模型、外部资料服务、技能等全局设置。
- 现有的历史研究和资料库全部归到管理员账号（用户本人）。

研究仍在 Web 进程里执行；研究引擎的能力和证据引用合同不变。

不做：

- 额度、用户自带 key（第 2 阶段）。
- Worker、任务排队、任务状态入库（第 3 阶段）。
- 自助找回密码、邮箱验证：内测由管理员用命令重置密码（已与用户确认）。
- 管理员网页（邀请码、用户列表）：第 1 阶段用命令行，见“待定事项”。
- 登录失败次数限制：第 4 阶段与限流一起做，见“出错时怎么办”。
- 线上部署变更（第 5 阶段）。
- 多用户下开放运行代码与浏览器（总体方案 §11）。

## 方案

### 1. 数据模型

第 1 阶段只建下面 6 张表。字段是设计意图，以迁移脚本为准。时间一律带时区、存 UTC（ADR 0006）。

| 表 | 字段 | 约束与索引 | 说明 |
| --- | --- | --- | --- |
| `users` | id、email、password_hash、role、status、created_at、updated_at | email 唯一；role ∈ {user, admin}；status ∈ {active, disabled} | email 存去掉首尾空格、转小写后的值 |
| `invites` | id、code_hash、created_by、note、expires_at、used_by、used_at、created_at | code_hash 唯一 | 邀请码只在生成时显示一次，库里只存哈希；created_by 为空表示命令行生成 |
| `sessions` | id、user_id、token_hash、created_at、last_seen_at、expires_at、revoked_at | token_hash 唯一；索引 user_id | 见 §2 |
| `conversations` | id、user_id、created_at | 索引 (user_id, created_at) | id 沿用现有 `conversation_id`（即首轮的 run_id） |
| `research_tasks` | id、user_id、conversation_id、query、created_at | 索引 (user_id, created_at) | 用户的一次研究请求（首问或追问） |
| `run_attempts` | id、task_id、run_id、created_at | run_id 唯一 | 一次实际执行，对应 `runs/<run_id>/`；第 1 阶段每个任务恰好一条 |

与总体方案 §5 的不同：

- `research_tasks` 先不加 `status`、`plan`、`config_snapshot`、`idempotency_key`、`cancel_requested_at`；`run_attempts` 先不加 `worker_id`、`status`、`heartbeat_at` 等。**第 1 阶段运行状态仍以 `meta.json` 为准**，只有一处写状态，避免数据库和文件不一致。第 3 阶段 Worker 接管执行时，再把状态移入数据库。
- 先建 `research_tasks` + `run_attempts` 两张表，而不是一张临时的 `runs` 表：结构与第 3 阶段一致，以后只加列，不搬数据。
- 暂不建 `library_documents`：资料库按用户分目录（§3.4），归属由目录保证；以后需要按用户统计或分页时再建。

### 2. 账号与登录

依据 ADR 0005（服务端会话 + HttpOnly Cookie）。

**接口**

| 接口 | 登录要求 | 说明 |
| --- | --- | --- |
| `POST /api/auth/register` | 否 | `{invite_code, email, password}`。同一事务内建用户（role=user）并把邀请码标为已用；成功后直接登录 |
| `POST /api/auth/login` | 否 | `{email, password}`；成功后设置 Cookie |
| `POST /api/auth/logout` | 是 | 吊销当前会话，清除 Cookie |
| `GET /api/me` | 是 | `{id, email, role}`；前端据此判断是否已登录、是否管理员 |

**密码**

- argon2id 哈希（`argon2-cffi`，默认参数）。登录时如发现参数已过时，顺便重新哈希。
- 长度 8–256 个字符（新增限制）。下限防止过弱；上限防止超长输入拖慢哈希。

**会话**

- 登录成功生成 32 字节随机令牌，放进名为 `dra_session` 的 Cookie；库里只存令牌的 SHA-256。
- Cookie：`HttpOnly`、`SameSite=Lax`、`Path=/`；按请求的实际协议，HTTPS 时加 `Secure`。
- 有效期：**30 天无活动即过期**（新增限制）。有活动时延长：距上次记录活动超过 1 天才更新 `last_seen_at` 和 `expires_at`，避免每个请求都写库。
- 登出、管理员重置密码、停用账号时，吊销该用户相关会话，立即生效。

**每个请求怎么识别用户**

- 新增依赖 `current_user`（放在 `src/dra/api/deps.py`，方式同 #18）：读 Cookie → 查未过期、未吊销的会话 → 查用户（需 `status = active`）。失败返回 `401 未登录或登录已过期`。
- `current_user` 写成普通 `def`，内部开一个短会话，查完即关闭，只返回普通的用户数据（编号、邮箱、角色）。不用请求级 `yield` 依赖持有会话，否则进度流这类长连接会一直占着数据库连接（ADR 0006 规则 1、5）。
- 除 `/api/auth/register`、`/api/auth/login`、`/healthz` 和前端静态文件外，所有 `/api/*` 都要求登录：在各 router 上统一挂依赖，并加一个测试遍历路由表，检查没有遗漏。
- 跨站请求伪造：`SameSite=Lax` 之外，对 POST/PUT/PATCH/DELETE 检查 `Origin` 头；带了且不是本站的返回 403。

**错误信息**

| 情况 | 返回 |
| --- | --- |
| 邀请码不存在、已用、已过期 | 400 `邀请码无效或已使用` |
| 邮箱已注册 | 409 `该邮箱已注册` |
| 邮箱不存在或密码错误 | 401 `邮箱或密码错误`（两种情况同一句话、相近耗时：邮箱不存在时也做一次哈希校验） |
| 账号已停用 | 403 `账号已停用` |

**管理命令**（`uv run python -m dra.admin <命令>`）

| 命令 | 作用 |
| --- | --- |
| `create-admin --email` | 建管理员账号，密码交互输入。库里还没有管理员时用它建第一个 |
| `create-invite [--days N] [--note 说明]` | 生成一个邀请码并打印一次；默认 14 天后过期（新增限制，可用 `--days` 改） |
| `migrate` | 把数据库升级到最新迁移（内部调用 Alembic）；部署、CI 和本机开发都用它 |
| `reset-password --email` | 交互输入新密码，吊销该用户全部会话 |
| `disable-user --email` / `enable-user --email` | 停用（同时吊销会话）或恢复账号 |

### 3. 归属校验

**规则**：凡是按编号访问的资源，先确认属于当前用户；不属于或不存在，一律返回 `404`，提示与“不存在”相同，不透露是否存在。管理员也只看得到自己的研究和资料，不能查看别人的。

#### 3.1 研究与对话

| 接口 | 校验 |
| --- | --- |
| `GET /api/runs`、`GET /api/conversations` | 从数据库查当前用户的 run_id / conversation_id，再读对应文件；返回格式不变 |
| `/api/runs/{run_id}` 及其下全部子路径（详情、事件、事件详情、来源、原件、图片、MCP 回执、产物下载与预览、执行日志、上下文检查点、研究材料、`simple`、`skills`） | run_id 必须属于当前用户 |
| `/api/research/{run_id}/stream`、`/followup`、`/messages`、`/cancel` | 同上 |
| `/api/conversations/{conversation_id}` | conversation 必须属于当前用户 |

- 业务层提供 `require_run(user, run_id)`、`require_conversation(user, conversation_id)`，找不到抛业务层的“不存在”错误，接口层翻译成 404（沿用 `service_errors()`）。
- #23 一并完成：`routers/` 里不再出现 `store._dir(`、`store.root /`，文件读取收进 `RunStore` 的方法。

#### 3.2 发起研究与追问

- 发起：在启动研究之前，同一事务内写入 `conversations`、`research_tasks`、`run_attempts`。写库失败则不启动研究，返回 503；此时还没建运行目录，不会留下残留。
- 线程与事件循环的交接（ADR 0006 规则 3）：`/api/research`、`/followup` 保持 `async def`。先生成 run_id，用 `await asyncio.to_thread(...)` 在线程里完成归属检查和写库这一个短事务，只带回普通数据；回到事件循环后，再调用 `RunRegistry.start_simple_research` 启动研究。数据库会话不离开那个线程。
- 进度流 `/api/research/{run_id}/stream`：同样先在线程里完成登录和归属检查、关闭会话，再返回流式响应；推送过程中不访问数据库。
- 追问：父研究必须属于当前用户；新一轮写入同一 conversation 下的新 `research_tasks` + `run_attempts`。
- `meta.json` 增加 `user_id`，便于排查；归属以数据库为准。
- 规划请求（`/api/brief*`）要求登录；`plans/<plan_id>/meta.json` 记录 `user_id`。这些记录没有读取接口，不需要归属校验。

#### 3.3 运行代码与浏览器的数据

执行日志、工作区、产物都按 run_id 存放，通过 §3.1 的 run 归属校验访问。多用户下是否开放运行代码与浏览器不在本阶段（总体方案 §11）。

#### 3.4 资料库

- 按用户分目录：`<数据目录>/library/users/<user_id>/`，目录内结构与现在相同。
- `get_library()` 改为按用户取得对应的 `LibraryStore`。别人的 `document_id`、`version_id` 在自己的目录里自然找不到 → 404；研究请求里填了别人的资料编号 → 400（沿用现有 `pin` 的报错“所选资料不可用，请刷新资料列表”）。
- **研究引擎不再自己调 `get_library()`**：发起研究时把当前用户的资料库对象随配置传入（`simple_research.py` 中 3 处）。引擎仍不知道“用户”这个概念。
- 嵌入模型、导入线程、并发名额**全进程共用一份**，不随用户数增加：现在每个 `LibraryStore` 会各自加载嵌入模型（`LocalEncoder`），按用户分开后若不共用，内存会随用户数成倍增长。

### 4. 管理员权限

只有管理员能调用的接口，普通用户调用返回 `403 需要管理员权限`：

| 类别 | 接口 |
| --- | --- |
| 研究设置 | `PUT /api/config`、`POST /api/config/test` |
| 外部资料服务 | `PUT /api/mcp/config`、`POST /api/mcp/test` |
| 模型服务商 | `POST /api/providers`、`PUT/DELETE /api/providers/{provider}`、`POST /api/providers/refresh`、`POST /api/providers/{provider}/refresh`、`PUT /api/providers/{provider}/model-metadata`、`POST /api/model-catalog/refresh` |
| 技能 | `PUT /api/skills/enabled`、`PUT /api/skills/packages/{name}` |

登录用户都能读：`GET /api/config`、`GET /api/mcp/config`、`GET /api/providers`、`GET /api/skills`、`POST /api/skills/prepare`、`GET /api/execution/status`。发起研究时要用这些信息选技能和外部资料。已核对这些接口不返回密钥值：服务商只返回 `key_configured`，MCP 配置只存环境变量名。

前端：普通用户的设置页不显示上表中的修改入口；管理员保持现状。

### 5. 旧数据导入

用命令导入，可重复执行：

```bash
uv run python -m dra.admin import-legacy --owner <管理员邮箱>
```

- **研究记录**：扫描 `runs/` 下所有目录，按 `meta.json` 的 `conversation_id`（没有则用 run_id）、`turn_index` 建 `conversations`、`research_tasks`、`run_attempts`，全部归到指定管理员。已在库里的 run_id 跳过，所以重复执行不会重复导入。
- **文件不动**：不移动、不改写任何运行目录，原 `run_id`、会话链、来源和证据编号保持原样。
- **读不了的目录**（`meta.json` 缺失或损坏）：跳过并在输出里逐个列出，不中断整体导入。
- **资料库**：把现有 `library/manifest.json` 和 `library/versions/` 移到 `library/users/<管理员 id>/`。这一步与 §3.4 同一个 PR 上线，避免出现“代码按用户找、文件还在旧位置”的中间状态。
- 输出汇总：导入几条、跳过几条（已存在 / 读不了）。

### 6. 测试

依据 ADR 0006。

- 默认 `uv run pytest`：每个测试一个临时 SQLite 文件，跑同一套 Alembic 迁移。不需要启动任何服务。
- `uv run pytest --run-postgres`：从 `DRA_TEST_DATABASE_URL` 读地址，同一批测试改连 PostgreSQL，再加跑只适用于 PostgreSQL 的测试。没给地址时报错，不静默改回 SQLite。
- 现有接口测试的登录：`conftest.py` 默认为每个测试建一个管理员并让请求以他的身份通过（FastAPI `dependency_overrides`）；登录、权限、归属相关测试关闭这个默认，走真实的 Cookie 流程。
- 不同环境的 PostgreSQL：
  - 本机：新增 `compose.dev-db.yaml`，一条命令 `docker compose -f compose.dev-db.yaml up -d` 启动；只用于开发，不改生产用的 `compose.yaml`。
  - CI 测试：`container-image.yml` 的 `backend-tests` 任务增加 PostgreSQL 服务和一步 `--run-postgres`。
  - CI 镜像冒烟检查：`build-test-publish` 任务现在直接 `docker run` 镜像并等健康检查。数据库成为必需后，同一步（实施第 1 步）里改为：在同一个 Docker 网络中先起一个临时 PostgreSQL 容器，用镜像执行迁移，再带 `DRA_DATABASE_URL` 启动 Web 容器做健康检查，结束后清理两个容器和网络。
  - 镜像里能执行迁移：镜像只拷贝 `src/`，而且不带 `uv`（冒烟检查明确要求没有 `uv`）。因此迁移脚本放在 `src/dra/migrations/`，由 `python -m dra.admin migrate` 执行（内部调用 Alembic），不依赖仓库根目录的文件。
  - 云端开发环境：镜像自带 PostgreSQL 16，环境初始化脚本启动它（实施第 2 步时实测后再加）。
- 迁移测试：空库升级到最新；在导入了样本旧数据的库上升级到最新。

### 7. 运行时配置

| 变量 | 用途 | 默认 |
| --- | --- | --- |
| `DRA_DATABASE_URL` | PostgreSQL 连接地址（`postgresql+psycopg://...`） | 无，必填。没配时 Web 启动失败并提示，不静默降级 |
| `DRA_TEST_DATABASE_URL` | 仅测试，配合 `--run-postgres` | 无 |

启动时检查：数据库可连接、迁移已是最新版本。不是最新时启动失败，并提示执行 `python -m dra.admin migrate`（开发时 `uv run python -m dra.admin migrate`）。不在启动时自动迁移，避免多个进程同时迁移，也让迁移成为一个看得见的步骤。

## 出错时怎么办

| 情况 | 处理 |
| --- | --- |
| 数据库连不上 | 接口返回 503；已在跑的研究继续写文件，但新研究无法开始（写不了归属） |
| 两人同时用同一个邀请码注册 | 用条件更新标记已用（`used_at IS NULL` 才更新），只有一个成功，另一个得到“邀请码无效或已使用”，其用户记录随事务回滚 |
| 同一邮箱同时注册 | 唯一约束保证只成功一个，另一个得到 409 |
| 研究进行中会话过期 | 研究不受影响（在后台线程执行，不依赖会话）；前端下次请求得到 401，跳转登录，登录后可继续查看 |
| 研究进行中账号被停用 | 研究继续到结束；该用户之后的请求被拒绝。第 1 阶段**管理员不能单独取消别人的研究**：取消接口按归属校验，管理员也会得到 404；研究在 Web 进程内存里，命令行也够不着。需要立即停止时，唯一办法是重启 Web 服务：沿用现有行为，重启时未结束的研究标为失败，已存材料保留（这会同时中断其他人正在进行的研究）。正式的管理员取消入口见“待定事项” |
| 发起研究时写库成功、启动失败 | 沿用现有启动失败的处理（`meta.json` 标失败）；数据库里的记录保留，该研究在列表里显示为失败 |
| 暴力猜密码 | 第 1 阶段不限制次数。注册需邀请码、线上暂未开放，风险可控；第 4 阶段做按 IP 和账号的限流。开放内测（第 3 阶段后）前必须完成，或在 Caddy 层先加简单限流 |

## 验收场景

| 场景 | 预期 |
| --- | --- |
| 用有效邀请码注册 | 账号建立并直接登录；邀请码变为已用 |
| 用已用、过期、不存在的邀请码注册 | 400，同一提示 |
| 两个请求同时用同一个邀请码 | 只有一个成功 |
| 邮箱大小写不同重复注册 | 409 |
| 密码错误 / 邮箱不存在 | 401，同一提示 |
| 未登录访问任一 `/api/*`（白名单除外） | 401 |
| 登出后用旧 Cookie 访问 | 401 |
| 重置密码或停用账号后，旧会话 | 立即 401 |
| 30 天无活动 | 会话过期，401 |
| A 访问 B 的研究详情、事件、来源、原件、图片、产物、执行日志、对话、进度流 | 一律 404，提示与不存在相同 |

| A、B 的历史列表、对话列表、资料库列表 | 各自只看到自己的 |
| 普通用户调用 §4 的修改接口 | 403 |
| 普通用户读设置、选技能、选外部资料服务 | 正常 |

| 在样本旧数据上执行导入 | 全部研究归管理员；来源、证据引用、报告、附件、会话链可正常打开；重复执行不重复导入；坏目录被列出 |
| 导入后普通用户 | 看不到任何旧研究 |
| 迁移 | 空库、已有数据的库都能升级到最新；默认测试和 `--run-postgres` 都通过 |
| 登录后发起研究、追问 | 研究正常启动并结束；数据库里有对应的归属记录；会话没有跨线程使用 |

| 多个用户使用资料库 | 嵌入模型只加载一份 |

## 新增的限制

实施时在对应 PR 再次列出：

- 注册需要邀请码（ADR 0003）；邀请码默认 14 天过期，一码一用。
- 密码 8–256 个字符。
- 会话 30 天无活动过期。
- 不能自助找回密码，由管理员用命令重置。
- 普通用户不能修改全局模型、外部资料服务、技能设置。
- 管理员也看不到其他用户的研究和资料。
- Web 服务必须配置 PostgreSQL 才能启动，且迁移须为最新。
- 第 1 阶段不限制登录失败次数（见“出错时怎么办”）。

沿用、会影响本流程的限制：SQLAlchemy 连接池默认常驻 5 条、临时最多再开 10 条、取不到连接等 30 秒；FastAPI 线程池默认 40 个线程（ADR 0006）。全站同时研究数 `DRA_MAX_ACTIVE_RUNS`（默认 1）不变，按全站计，不按用户计。

## 实施记录

### 第 1 步：接入数据库（#28）

按设计实现：`dra/db.py`（连接、按操作开关的短会话、启动检查）、`dra/db_tables.py`（`users`、`invites`、`sessions`）、迁移 `dra/migrations/versions/0001_*`、`python -m dra.admin migrate`、测试默认 SQLite + `--run-postgres`、`compose.dev-db.yaml`、CI 两种测试与镜像冒烟检查的数据库准备。

与设计不同或设计未写到的地方：

- **数据库地址可写在 `.env`。** `python -m dra.web` 启动时不会加载 `.env`（项目里 `.env` 是各模块用到时才读）。为了本机开发能把地址写进 `.env`，`DRA_DATABASE_URL` 没设时读项目 `.env` 里这一项，只读这一项、不写入进程环境；环境变量优先。离线测试把 `.env` 指向不存在的文件。
- **`/healthz` 增加数据库检查**（`SELECT 1`），连不上返回 503，与“出错时怎么办”中“数据库连不上 → 503”一致。镜像的 `HEALTHCHECK` 随之覆盖数据库。
- **`--run-postgres` 要求库名含 `test`**：测试开始时会清空整个 `public` schema，防止误指向开发库或正式库。这是只影响测试的新增限制。
- **迁移脚本不引用应用代码里的类型**：自定义的 UTC 时间类型在迁移里写成普通的 `sa.DateTime(timezone=True)`，`env.py` 生成新迁移时自动这样写；以后重命名应用代码里的类型不会破坏旧迁移。
- 仓库根目录另有 `alembic.ini`，只用于开发时生成新迁移（`uv run alembic revision --autogenerate`）；执行迁移仍用 `python -m dra.admin migrate`，镜像不依赖它。
- 云端开发环境的初始化脚本按设计留到第 2 步再加。

### 第 2 步：账号与登录（#29）

按设计实现：`services/auth.py`（注册、登录、会话、管理操作）、`routers/auth.py`（`/api/auth/register`、`/login`、`/logout`、`/api/me`）、`deps.current_user`（普通 `def`、短会话、返回普通数据）与 `same_origin`、除白名单外所有 router 统一挂登录依赖、`dra.admin` 的账号命令、前端登录/注册页与 401 回到登录页、测试默认管理员身份。

与设计不同或设计未写到的地方：

- **Cookie 在浏览器里保存 400 天**（浏览器允许的上限）。会话是否有效以服务端为准（30 天无活动过期、有活动延长）；如果 Cookie 跟着设成 30 天，活跃用户也会在登录 30 天后被踢出，而服务端延长时没法给进度流这类直接返回的响应补发 Cookie。
- **登录不在前端检查密码长度**，只在注册时检查：长度规则以服务端为准。注册页多一个“确认密码”，因为没有自助找回密码，输错就只能找管理员。
- **管理命令的密码**默认交互输入两次；脚本可用 `--password-stdin` 从标准输入读一行。密码不出现在命令行参数里。
- **`dra/admin.py` 是入口**：与 `web.py` 一样可以调用 `dra.api.services`，分层测试中“研究引擎不依赖接口层”这一条把它和 `web.py` 一起排除。
- **进度流断开时**，前端顺带请求一次 `/api/me` 判断是不是登录失效：浏览器的 `EventSource` 看不到状态码。
- **邀请码在条件更新那一刻被别人抢先用掉**的情况，用 PostgreSQL 上的确定性测试覆盖：在本次注册写入用户之后、标记邀请码之前，用另一条连接把它标为已用，确认本次注册失败并回滚。只靠多线程同时注册的测试在实测中线程会先后执行，去掉条件更新也能通过，证明不了什么。
- **审查修正（#34）**：
  - 开发代理改为显式 `changeOrigin: false`（`web/src/devProxy.ts`）。Vite 的字符串写法默认改写 Host，Origin 仍是 5173，同站检查会拒绝正常的登录、注册；`web/src/devProxy.test.ts` 经真实 Vite 代理核对后端收到的 Host 与 Origin。
  - 登录签发会话前，在用户行的行锁（`SELECT … FOR UPDATE`）下复核密码哈希和账号状态。慢的密码校验仍在事务外；重设密码、停用账号先改这一行再吊销会话，两边按行锁排队：重设先提交则登录被拒，登录先提交则新会话被随后的重设吊销。确定性测试覆盖两种顺序，PostgreSQL 上另有“重设未提交时登录等待行锁”的测试；去掉复核或去掉行锁，各自的测试都会失败。
  - “全部接口要求登录”的检查改为按行为验证：从 OpenAPI 文档列出全部 `/api/*` 接口与方法，逐个不带登录请求，断言 401（注册、登录除外），并断言检查到的数量（当前 57 个）。原检查遍历 `app.routes`，而 FastAPI 0.139 把 `include_router` 的子路由包在私有的 `_IncludedRouter` 里，实际一条都没查到。另有变异用例确认漏挂登录的子路由会被抓到；接口不得用 `include_in_schema=False`，否则会漏查。
  - 退出只在服务端确认（成功或 401）后回到登录页；503、网络失败时保持登录，显示“退出登录失败……当前仍处于登录状态”和重试按钮。
- **云端开发环境**：初始化脚本启动容器自带的 PostgreSQL 16，建 `dra_dev`、`dra_test` 并迁移；环境变量 `DRA_DATABASE_URL`、`DRA_TEST_DATABASE_URL` 指向这两个库（账号密码只在容器内有效）。

### 第 3 步：研究记录入库与旧数据导入（#30）

按设计实现：`conversations`、`research_tasks`、`run_attempts` 三张表（迁移 `0002`）；`services/run_records.py`（占位、撤销、旧数据导入）；`services/runs.start_owned_research` / `start_owned_followup` 在接口的 `async def` 里经 `asyncio.to_thread` 写库，再在事件循环上启动研究（ADR 0006 规则 3）；`meta.json` 与 `plans/<id>/meta.json` 记录 `user_id`；`python -m dra.admin import-legacy`。

与设计不同或设计未写到的地方：

- **先占位、再启动、失败就撤销。** 设计只写了“写库失败则不启动研究”。实施时发现另一半：写库成功后启动也可能失败（名额已满 429、计划不一致 400、MCP 不可用……），这时把刚写的三行删掉（补偿操作），原错误照常返回，避免留下“有记录、没运行目录”的研究。撤销本身失败只记日志，不盖住原错误。
- **重复提交同一个追问**（同一 `request_id`）时，现有逻辑返回之前那一轮的编号、不再启动；这时同样撤销本次占位。
- **对还没导入的旧研究追问，直接拒绝**（409，提示先执行 `import-legacy`），不自动认领（用户 2026-11-07 确认）。
- **第 3 步不检查对话属于谁**，追问时不判断父对话是否属于当前用户，留到第 4 步统一做（用户 2026-11-07 确认：第 4 步合并前不会有其他用户）。
- **导入命令**：
  - 只登记到管理员名下，`--owner` 不是管理员时拒绝。
  - 以点开头的目录（如执行工作区 `.workspaces`）和非目录直接忽略。
  - 目录名不是研究编号、`meta.json` 缺失或损坏、`meta.json` 里的 `run_id` 与目录名不一致，都列为“读不了”，逐个列出，不中断整体导入。
  - 对话和请求的创建时间取 `meta.json` 的 `started_at`。
  - 多了 `--runs-dir` 参数，默认 `<数据目录>/runs`，便于对别处的目录导入和测试。
- 数据库连接类故障翻译成“暂时不可用”（503）的工具从 `services/auth.py` 抽到 `services/db_errors.py`，两处共用。
