# 开发流程

日期：2026-11-05。适用于人和 AI 工具（Codex、Claude Code）。硬性规则摘要在 [AGENTS.md](../AGENTS.md)，这里是具体做法。

## 总览

```text
开 issue → 拉分支 → 开发（独立工作目录）→ 开 PR → 另一个 AI 审查 → 用户合并
```

一件事 = 一个 issue = 一个分支 = 一个 PR。

## 1. 开 issue

- 在 GitHub 新建 issue 时选“任务”或“问题反馈”模板；用 `gh issue create` 时按模板的小标题填写正文。
- 必填：背景、要做什么、不做什么、验收标准、影响的限制。
- “不做什么”用来划定范围，防止改动越做越大。
- 一个 issue 应能在一个 PR 内做完、讲清楚。太大就拆成几个 issue，用里程碑串起来。
- 需要写 ADR 或设计文档的（判断标准见 [开发规范 §7](开发规范.md#7-设计文档与-adr)），打 `需要设计` 标签：先开设计 PR，合并后再开代码 PR。

标签：

| 类别 | 标签 |
| --- | --- |
| 类型 | `类型:功能` `类型:bug` `类型:重构` `类型:文档` `类型:评测` |
| 模块 | `模块:后端` `模块:前端` `模块:研究引擎` `模块:部署` |
| 谁在做 | `agent:codex` `agent:claude` |
| 流程 | `需要设计` |

## 2. 拉分支

- 从最新的 `main` 拉：`<类型>/<issue号>-<简述>`，例如 `refactor/12-split-web-routes`。
- 类型：`feat` 新功能、`fix` 修 bug、`refactor` 重构（功能不变）、`docs` 只改文档、`eval` 评测。
- AI 在独立工作目录（git worktree）里开发，互不干扰：

  ```bash
  git fetch origin
  git worktree add ../rw-12 -b refactor/12-split-web-routes origin/main
  ```

  根目录的 `.worktreeinclude` 列出新工作目录需要从本机复制的配置文件（如 `.env`），这些文件仍被 Git 忽略。
- 做完合并后删掉工作目录：`git worktree remove ../rw-12`。

## 3. 开发与提交

- 动手前先看相关代码、测试和 `docs/adr/` 里的决定。
- 提交信息用中文一句话写清结果，例如：`拆出研究相关接口到 routers/research.py，行为不变 (#12)`。
- 默认只跑离线测试；需要真实模型、付费搜索、Docker 时先问用户。
- 发现 issue 范围外的问题：开新 issue 记下，不在当前分支顺手改。

## 4. 开 PR

- AI 推送功能分支后用 `gh pr create` 开 PR，正文按模板填写，写上 `Closes #<issue号>`，合并时 issue 自动关闭。
- 模板要求写清：改了什么（大白话）、实际跑了哪些测试、哪些没验证、限制有没有变化、由哪个 AI 写的。
- 改了界面的附截图。

## 5. 交叉审查

- Codex 写的 PR 由 Claude Code 审（`/code-review <PR号>`），Claude Code 写的由 Codex 审。
- 审查意见写在 PR 评论里；作者 AI 逐条回应：已改、不改（说明理由）。
- 用户看 PR 描述和审查结论决定是否合并。

## 6. 合并

- 合并条件：CI 通过 + 用户同意。
- 合并方式：Squash（压成一个提交），`main` 上一个 PR 一条记录。
- 合并后删除远程分支和本地工作目录。

## 开发技能

开发技能是给写代码的 AI 用的操作步骤，放在 `.claude/skills/`，与产品里给研究 Agent 用的“技能”（`src/dra/builtin_skills/`）无关。

| 技能 | 何时用 |
| --- | --- |
| [finish-task](../.claude/skills/finish-task/SKILL.md) | 任务做完：选测试、推送、按模板开 PR |
| [handoff](../.claude/skills/handoff/SKILL.md) | 任务没做完要停下：把进度写到 GitHub，供另一个 AI 或会话接手 |

Claude Code 自动加载该目录；Codex 及其他工具按 AGENTS.md 的提示直接读对应 `SKILL.md`。新增技能的条件：反复要做、超过三四步、AI 容易漏步，三条都满足；先在真实任务里用过再定稿。

## 跨会话接手

- 进度以 GitHub 为准，不依赖某个 AI 的聊天记录。
- 接手前先读 issue、PR 描述和最近一条“交接”评论，再看分支上的提交。
- 同一分支同一时间只有一个会话在改。

## AI 权限

| 可以自己做 | 必须先问用户 |
| --- | --- |
| 读代码、跑离线测试 | 真实模型、付费搜索、Docker、外部服务 |
| 在功能分支提交、推送功能分支 | 推送 `main`、合并 PR |
| 开 issue、开 PR、写审查评论 | 发布上线、登录服务器 |
| 新增 ADR 草稿 | 推翻已接受的 ADR |

## 例外

- 线上紧急故障：仍走 PR，但可以先合并、后补审查，事后在 PR 里写明原因。
