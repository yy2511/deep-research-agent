# 技能加载与执行环境设计待办

状态：**暂不改动**，记录问题与方案，后续有空再做。记录日期 2026-10-12。

## 1. 现状

- 系统提示词只披露技能目录（名称、标题、简介），见 `src/dra/skills.py` 的 `disclosure()`，注入位置 `src/dra/simple_research.py` 约第 4654 行。
- 模型用 `load_skill(name)` 取正文，用 `read_skill_reference(name, path)` 取参考材料；后者要求先加载正文（`skills.py` 约第 294 行）。
- 手选技能：主 Agent 启动时由系统代调 `load_skill`（记为 `manual`，`simple_research.py` 约第 4655–4661 行）；澄清和规划阶段由 `web.py` 约第 427 行直接把正文拼进规划提示词。
- 子 Agent 也能看到目录并自行加载；手选预加载只作用于主 Agent。
- 已加载内容不重复注入，总量受 `MAX_ACTIVE`（60,000 字符）限制；每次加载记录版本哈希与加载者。
- 触发说明（`skills.py` 第 23–26 行）只有一句：“按相关性调用 load_skill(name)，不要只凭简介猜测正文。”

## 2. 发现的问题

1. **自动加载几乎不发生。** 2026-10-07 的 DeepSeek 24 题真实评测中，每题首个请求都带技能目录和加载工具，但主、子 Agent 实际加载次数均为 0（见 STATUS.md 对应批次）。
2. **触发规则偏弱。** 与 Codex 的技能说明相比，缺少“明显匹配时必须使用”“说明用了哪个技能；跳过明显相关的技能要说明原因”等约束。这是加载 0 次最可能的主因，与用哪种工具读取无关。
3. **两个工具可合并。** 正文和参考材料可以由同一个入口提供。
4. **子 Agent 自行加载**，可能造成方法不一致和重复加载。Codex 的规则相反：由主 Agent 自己读技能，不把阅读和理解技能交给子 Agent。
5. **无法用通用读取工具获取技能。** 根因是 `read_file` 在执行环境内运行：`execution.py` 第 415–436 行的 `session.tool()` 先 `self.start()` 启动执行环境，再通过环境内辅助程序读取。因此：
   - 不开执行环境就没有 `read_file`，而技能必须在这种情况下也能用；
   - 只读一个文件也要先启动 Docker；
   - 技能存放在后端数据目录，本来就不在沙箱工作区内。

   所以在现有架构下，专门工具是必需的，不是设计失误。

## 3. 其他开源 harness 的做法（2026-10-12 查阅源码）

| 项目 | 沙箱范围 / 读文件在哪里执行 | 技能读取方式 |
|---|---|---|
| OpenAI Codex | 沙箱只管 shell 命令；`SandboxPolicy` 默认可读整盘，只限制写入与网络 | 技能在本机：模型用 shell 读 `SKILL.md`；技能在执行环境或云端：用专门的 `skills.read({package, resource?})`（单一工具）。通过观察命令识别隐式使用；另有检索式技能选择器（BM25、字符 n-gram、RRF 等）处于 shadow 实验阶段 |
| Claude Code | 沙箱（SRT）只管 Bash；`Read` 在 harness 进程内执行，靠权限规则控制 | `Skill` 工具加载正文，参考文件用 `Read` 读 |
| Gemini CLI | 读文件受工作区可访问目录约束 | `activate_skill(name)` 返回正文和目录树，并把技能目录加入可读范围，之后用通用 `read_file` 读；非内置技能激活前需用户确认 |
| OpenCode | 文件工具在 harness 内执行，靠权限规则控制 | `skill(id)` 返回正文、目录和文件列表，参考文件用通用工具读；`autoinvoke: false` 的技能只能由用户调用，不展示给模型 |
| OpenHands SDK | 文件与命令都经过工作区抽象（本机或远程容器） | `invoke_skill` 返回正文和位置；另支持关键词触发，系统自动注入技能 |
| LangChain deepagents | 文件操作经过 backend 抽象；`CompositeBackend` 按路径前缀分发到不同存储 | 没有专门工具，模型直接用 `read_file` 读技能路径 |

共同规律：读文件与执行命令分离。沙箱主要管命令；读文件要么在 harness 内执行，要么经过可分发的存储抽象。技能放在读文件工具能访问的位置，所以能用通用工具读。

源码位置：
- Codex：`codex-rs/protocol/src/protocol.rs`（SandboxPolicy）、`codex-rs/ext/skills/src/catalog_prompt.rs`、`invocation.rs`、`dynamic_skill_selector.rs`
- Gemini CLI：`packages/core/src/tools/activate-skill.ts`
- OpenCode：`packages/core/src/tool/plugin/skill.ts`、`packages/core/src/skill/instructions.ts`
- OpenHands：`openhands-sdk/openhands/sdk/tool/builtins/invoke_skill.py`、`openhands-sdk/openhands/sdk/context/agent_context.py`
- deepagents：`libs/deepagents/deepagents/backends/composite.py`、`libs/deepagents/deepagents/middleware/skills.py`

## 4. 候选方案

### 方案 A：保留专门工具，合并成一个（改动最小）

- `load_skill(name, path=None)`：不传 `path` 返回正文和参考文件列表；传 `path` 返回参考文件（要求已加载正文）。
- 保留版本哈希、加载者记录、去重、“不是证据”标记与总量限制。
- 与 Codex `skills.read`、OpenHands `invoke_skill` 同一模式。

### 方案 B：把 `read_file` 上移到 harness 层，按路径分发（架构更干净）

- `/workspace/...`：直接读会话工作区（本机目录），不启动执行环境。
- `/skills/<name>/...`：只读，从技能存储读取（类似 deepagents `CompositeBackend`）。
- `load_skill(name)` 只返回正文和文件列表；参考文件用通用 `read_file`。
- 按路径前缀记录技能使用情况。
- 收益不限于技能：还解决“读一个文件也要启动 Docker”的问题。
- 需重新划定安全边界：不开执行环境时 `read_file` 也可用但只放行这两个前缀；`/skills` 只读；路径防越界。

### 不采用：把技能复制进沙箱

会让技能依赖执行环境，每次还要启动容器。

## 5. 建议顺序

1. **先改触发说明**（成本最低）：加入“明显匹配时必须使用”“说明使用了哪个技能；跳过明显相关的技能要说明原因”。离线测试后，经用户确认再用少量真实题验证加载次数是否变化。
2. **方案 A**：合并为单一工具。
3. **另行评估**：规划阶段推荐技能（或借鉴 Codex 用检索做候选）；子 Agent 加载权限是否收回主线；方案 B 作为“文件读取与沙箱解耦”的独立改动评估，不单为技能去做。

## 6. 执行环境（沙箱）机制

### 6.1 启动时机

不是会话一开始就创建，而是在第一次调用执行类工具（`bash`、`read_file`、`write_file`、`edit_file`、`download_source`、`export_research_materials`）时按需创建（`src/dra/execution_tools.py` 第 138–157 行 `_session()`）。

- 前提：设置中开启“运行代码”（`execution.enabled`）且所选环境可用；否则明确报错，不退回无隔离的本机执行。
- 一次研究只创建一个实例，子 Agent 通过 `execution_owner` 共用主线实例；追问时接回同一会话工作区。
- 没有调用执行类工具的研究不会启动 Docker。

### 6.2 沙箱管什么

**所有执行类工具都经过沙箱，包括读写文件。** `bash`、`read_file`、`write_file`、`edit_file` 都走 `session.tool()`（`src/dra/execution.py` 第 415 行起），先 `self.start()` 启动执行环境，再由环境内的辅助程序完成操作。搜索、网页阅读、存证、看图、浏览器和受控下载不在沙箱内，各有独立的执行路径。

### 6.3 两种后端

| 项目 | Docker（默认） | 本机系统沙箱（`native`） |
|---|---|---|
| 平台 | 需要 Docker | 仅 macOS，SRT 0.0.78 / Seatbelt |
| 文件系统 | 容器根目录只读；会话的 work/output 可写；input 只读挂载；tmpfs 临时目录 | 只开放本会话 work/output 和专用临时目录写入；input 与必要系统运行时只读；用户 home、项目配置、其他工作区不开放 |
| 网络 | `network_mode`：`none`（默认）或 `bridge` | 外网经 HTTP(S)/SOCKS 代理；回环、私网、宿主地址（含 DNS 解析结果）一律拒绝 |
| 资源 | 内存默认 2048 MB、进程数 128、1 个 CPU；`cap_drop=ALL`、`no-new-privileges`、非 root 用户 | 没有 CPU/内存/进程数配额 |
| 生命周期 | 24 小时租期，使用时续期（至多每 10 分钟一次）；服务重启时清理遗留容器 | 取消/超时终止命令所在进程组；不能保证回收自行脱离进程组的守护进程 |
| 依赖 | 每个会话独立的 Python/Node 依赖目录，可 `pip install` / `npm install`，追问可复用 | 同左 |

共同规则：

- 单条命令默认 30 秒，最高 120 秒；Bash 次数默认不限（`max_commands=None`，显式配置时仍生效）。
- “仅我的资料”模式始终关闭执行联网（`execution_tools.py` `_config()`）。
- 只有在联网允许时才提供 `download_source` 和 `bash(fetch=...)`。
- `bash` 用 `source_refs` 声明输入时，成功输出登记为计算来源，可存证；Agent 自行 `curl` 下载的文件只算工作材料。

## 7. 与其他 harness 的沙箱对比（2026-10-12 查阅源码）

| 项目 | 沙箱技术 | 沙箱范围 | 读权限 | 读文件工具在哪里执行 |
|---|---|---|---|---|
| **本项目** | Docker 或 macOS Seatbelt（SRT） | 所有执行类工具，**包括 `read_file`** | 仅会话工作区与必要运行时 | 沙箱内（需先启动执行环境） |
| OpenAI Codex | macOS Seatbelt；Linux bubblewrap（`codex-rs/linux-sandbox`）；另有 Windows 沙箱 | 模型执行的 shell 命令 | `SandboxPolicy` 的 `ReadOnly`/`WorkspaceWrite` 可读整盘，只限制写入与网络；可写目录下 `.git`、`.codex` 等保持只读 | 没有独立读文件工具，用沙箱内 shell 读 |
| Claude Code | SRT（sandbox-runtime，与本项目 native 后端同一组件） | Bash | 由沙箱配置决定 | `Read` 在 harness 进程内执行，靠权限规则控制 |
| Gemini CLI | 两层：①整个 CLI 进程放进 docker / podman / sandbox-exec / runsc（gVisor）/ lxc，挂载当前目录，不挂载凭据；②较新的按命令沙箱（Linux bwrap、macOS Seatbelt，`packages/core/src/sandbox/`） | ①整个进程；②单条命令 | macOS 配置文件中 `(allow file-read*)`，读任意位置，限制写入与网络 | 读文件受工作区可访问目录约束；激活技能时把技能目录加入可读范围 |
| OpenHands SDK | 工作区抽象：本机或远程容器 | 文件与命令都在工作区内 | 工作区范围 | 工作区内 |
| LangChain deepagents | backend 抽象：内存、本机目录、本机 shell、沙箱服务等 | 由 backend 决定 | 由 backend 决定 | 经 backend；`CompositeBackend` 可按路径前缀把读取分到不同存储 |

源码位置：

- Codex：`codex-rs/protocol/src/protocol.rs`（`SandboxPolicy`、`WritableRoot`）、`codex-rs/linux-sandbox/`、`codex-rs/exec-server/src/sandbox_integrity/`
- Gemini CLI：`packages/cli/src/config/sandboxConfig.ts`、`packages/cli/src/utils/sandbox.ts`、`packages/cli/src/utils/sandbox-macos-*.sb`、`packages/core/src/sandbox/`
- deepagents：`libs/deepagents/deepagents/backends/`

### 对比结论

1. **主流做法是读宽写窄。** Codex 和 Gemini CLI 的沙箱默认允许读取几乎任意位置，重点限制写入和网络。本项目对读取也做了隔离，更严格，但代价是读文件必须依赖执行环境。
2. **主流做法把读文件和执行命令分开。** Claude Code、OpenCode 的读文件工具在 harness 内执行；deepagents 用可分发的 backend。本项目把读写文件和命令放在同一个沙箱会话里，这正是技能无法用通用 `read_file` 读取的根因（见第 2 节问题 5）。
3. **本项目更严格的地方有其理由**：研究会下载和处理不可信的外部文件，Agent 也可能联网安装依赖。严格的读隔离可以防止外部内容诱导 Agent 读取宿主机上的密钥或配置。如果采用方案 B（`read_file` 上移到 harness 层），必须保证它只能读会话工作区和 `/skills` 两个前缀，不能变成读宽。
4. **本项目已有、别家较少见的点**：计算结果可登记为可存证来源（记录输入哈希与命令）；网络代理同时拒绝私网地址和私网 DNS 解析结果；没有“沙箱不可用就退回本机直接执行”的静默降级。
