# 评测迭代总结（2026-09-29 至 10-14）

这份文档总结用评测发现问题、修改、再验证的过程。各项细节和原始数据见 [STATUS.md](../STATUS.md)、[eval/README.md](../eval/README.md)、[eval/deepsearchqa/README.md](../eval/deepsearchqa/README.md)，运行产物在 `eval/*/runs/`（不入库）。

## 一、用了哪些评测

| 评测 | 测什么 | 用法 |
|---|---|---|
| DeepSearchQA（DSQA，900 题） | 有明确答案的多步查找题，按答案集合算 F1 | 主力。小样本试跑 → 固定困难 50 题（hard50）反复对照 → 900 题全量 |
| BrowseComp-Plus（BCP） | 固定文档库 + BM25，排除真实网络的干扰，专门看框架本身 | 接通官方评分与官方标准 Agent 对照组，3 题试跑 |
| DeepResearch Bench II（DRB2） | 长报告质量：信息召回、分析、表达 | 2 道中文题试跑，用来调交稿提示词 |

评分口径：DSQA 从 10-04 起统一用官方的 Gemini 2.5 Flash 评分模板，给它完整原文。在这之前用的是 GPT-5.5 临时裁判加答案抽取，两种分数不能直接比较。

## 三、逐项迭代

### 1. 长 PDF 读不到后半部分

- **问题和表现**：DSQA 试跑第 699 题（蝙蝠考察名单），Agent 找到了官方报告，却反复说"未能确认名单"，复核后记 0 分。
- **原因**：网页正文只保存前 20 万字符。这份 PDF 有 474 页、约 127 万字符，目标表格在大约第 91 万字符处，Agent 根本拿不到。
- **方案**：正文默认完整保存（`storage_max_chars=None`）。长文改用"查找 / 按范围读 / 续读"取后面的内容，引用仍按原文位置绑定。
- **为什么这么选**：截断是我们自己加的限制，不是模型能力不够。保留全文、按需分段读，既不撑爆上下文，也不会丢内容。
- **效果**：699 题复跑 5 个答案全中，F1 从 0 到 1，用时 132 秒、只搜了 1 次。百万字符样本的末尾也能查到并正确引用。

### 2. 评分口径不可靠

- **问题和表现**：临时裁判把答案里"背景名单"的条目当成了候选答案，算了命中和多答。同一份回答换个裁判，分数就不一样。
- **原因**：用的不是官方评分模型（GPT-5.5 代替 Gemini 2.5 Flash），交给裁判之前还先抽取和清洗了答案，又多一层出错的机会。
- **方案**：改用官方 Gemini 2.5 Flash 和官方模板，把完整原文交给它，只去掉首尾空白，不抽取答案。另写了 `regrade_originals.py`，可以把已有结果单独重新评分。
- **为什么这么选**：只有评分和官方一致，分数才有参照价值。不做抽取，才能排除"抽错了"这种干扰。
- **效果**：已完成的 552 题重评，平均 F1 81.09%，512 次请求零失败。可配对的 551 题里有 41 题分数变化（35 升 6 降），说明裁判口径本身就能带来约 2 个点的差异，以后所有结果都按这个口径。

### 3. 提示词三组对照

- **问题和表现**：手上有几版系统提示词（原版、Claude 修改版、精简的 V2），不知道该用哪个。
- **原因**：之前每次改提示词都只看几道题，结论被随机波动淹没了。
- **方案**：固定 hard50（固定随机种子从历史不满分题里挑），三组共用同一个冻结的引擎，只换提示词，每组各跑一遍，逐题比较。
- **为什么这么选**：同一批题、同一个引擎、只改一处，才能把差异归到提示词上。挑难题是因为简单题三组都会满分，拉不开差距。
- **效果**：选定"原版 + Claude 修改"作为产品默认（F1 70.97%，26/50 满分）。这组 50 题后来一直当回归集用。

### 4. 评测配置和网页实际使用不一致

- **问题和表现**：旧的全量批次写死用 V2 提示词，没有研究计划，也不加载技能、不看图、不运行代码，测出来的不是用户实际用的产品。
- **原因**：评测脚本是早期写的，网页加了新功能后，评测没跟上。
- **方案**：停掉旧批次，新的评测入口和网页一致：先出计划（不问澄清问题）、用同一份技能目录、看图跟随网页设置、Docker 运行代码、开放原件下载。下载前后都过滤答案网站；Bash 联网不经过这层过滤，所以每题结束后再扫描一遍有没有泄题。
- **为什么这么选**：评测要回答的是"用户用到的东西好不好"。配置不一致，分数再高也说明不了问题。
- **效果**：hard50 从 70.97% 提高到 79.5%（31 题满分）。这一步同时改了好几项，不能单独归因。

### 5. 交稿提示词与报告质量（DRB2）

- **问题和表现**：DRB2 两题的"分析"项得分很低（15 项里只拿到 3 项），报告基本是带引用的事实罗列。还暴露出：限定了时间范围的题，被推去用最新资料；中文题收尾时交出了英文报告。
- **原因**：提示词只强调"每句话要有出处"，没有要求写因果和比较。"核对最新资料"这条规则被用到了限定年份的题上。回答语言靠模型自己判断。
- **方案**：交稿提示词要求在有引用的事实之上写因果、比较和总结，推断要标明。用户限定了时间范围时，范围外的资料只作背景。回答语言改由代码根据原问题判定，写进提示词。
- **为什么这么选**：分析是报告的价值所在，但不能借"分析"引入没有证据的新事实，所以要求分析句注明依据的卡片。
- **效果**：idx 43 的分析项从 5/11 提高到 8/11（总分 51.1% → 59.8%）；idx 15 因为交稿出错，总分从 54.5% 降到 41.8%。只有 2 题、各跑一次，**没有定论**。

### 6. 上下文压缩反而让结果变差

- **问题和表现**：开着会话压缩，用 64K 工作窗口跑 3 道题，一道都没交出实质答案，压缩本身就占掉了大量调用和时间。
- **原因**：窗口太小，压缩被频繁触发；摘要超时、或者摘要格式不合格被拒，最后因为本地估算的容量不够而停止。
- **方案**：同样 3 题依次试了 256K 和 128K。评测固定关闭压缩；关闭压缩时也不再按本地估算的容量拦截请求，直接发给服务商。
- **为什么这么选**：本地估算很保守，实际请求超过估算值时服务商照样正常返回。很多次"装不下"是我们自己估出来的，不是真的超了。
- **效果**：3 题实质交付从 0/3（64K）到 2/3（256K），再到 3/3（128K）。取消本地拦截后，4 道原来卡在容量上的题复测，平均 F1 从 48.5% 到 52.4%，没有再出现容量问题。

### 7. 隐藏的停止条件提前结束研究

- **问题和表现**：第 68 题，主 Agent 连续三次等待子任务（子任务都在正常运行），被判为"无进展"强制收尾。子任务后来找到的关键数据没用上，最后 0 分。
- **原因**：程序有一条"连续三轮无进展就停"的规则，而"等待子任务"被算成了没有进展。
- **方案**：删掉"连续三轮无进展"。研究只在模型交稿、用户叫停、时间或调用次数用完、服务故障时结束。工具报错只告诉模型，不触发停止。总时限改成可选。Bash 不再限 20 次。
- **为什么这么选**：遇到困难时该不该放弃，应该由模型根据实际情况决定，而不是一条看不见的硬规则。时间和预算由用户设定，更透明。
- **效果**：这类误停不再出现。代价是：如果总时限和次数限制都关掉，模型反复犯同一个错时程序不会叫停，只能由用户停止。

### 8. 模型请求超时导致空答

- **问题和表现**：第 68 题复测，第二轮模型请求两次各等约 91 秒都超时，整轮直接以空答结束，用时才 4 分钟。
- **原因**：研究请求只重试 1 次。中转服务白天首字延迟要 10–50 秒，偶尔更慢。
- **方案**：研究请求最多重试 10 次（指数退避，受截止时间约束），后来单次等待也延长到 240 秒。输出被额度截断时不执行，提示模型继续。
- **为什么这么选**：一次网络波动就作废整题，代价太大。重试受总截止时间约束，不会无限拖延。
- **效果**：全量 850 题里 16 道没交答案的题，原因都是卡死或时间用完（见第 9、10 项），没有统计到因单次请求超时而空答的题。这一项没有做专门的对照测试。

### 9. 保存证据时程序卡死几个小时

- **问题和表现**：全量夜跑中，有的题 40 分钟时限早过了还在跑：35、469 号进程 CPU 跑满空转 1–5 小时，399、798 跑到 2–2.3 小时才结束。
- **原因**：保存证据时，系统要在原文里定位模型摘的那段话。模型把三千多字的整张表格当摘录，原文又和摘录略有出入时，旧的近似搜索算法（fuzzysearch，纯 Python）要算一两个小时。而且它在研究线程里同步执行，时限也打断不了。离线复现：3375 字摘录对 4000 字原文，超过 150 秒。
- **方案**：换成 Myers 位并行算法，算的还是精确编辑距离。门槛、去重、候选数量都不变，只是快了。只有真正返回给模型的候选才计算差异明细。
- **为什么这么选**：先找更快的算法，而不是给摘录加长度上限或超时。加上限会改变产品行为，挡住合理的长摘录，换算法则不用。
- **效果**：把本机 1820 次运行里的 40,638 段摘录离线重放了一遍：40,564 段新旧结果一致；72 段旧算法 20 秒内算不完，新算法全部算完（中位 0.085 秒，最长 12 秒）；2 段只有候选结尾差几个字符。原来卡死的 798 号摘录，在 2.1 万字原文上 0.78 秒定位完成。

### 10. 时间到了交不出答案

- **问题和表现**：850 题里有 16 题没交答案：4 题是上一项的卡死，12 题是时间用完。第 51 题两次交稿都被"还有子任务在运行"挡回。
- **原因**：原来只在剩 120 秒时提醒，工具照常可用。模型收到提醒后还在检索、跑代码，最后一次请求被时限直接掐断，没有收尾环节。
- **方案**：总时限里预留 5 分钟交稿时间（网页设置"交稿时间"，最多占总时限一半）。研究阶段到点后停掉研究工具、取消子任务，已存的证据保留，然后只允许交稿一次，总时限不延长。正好跨过截止的那一轮里，存证和交稿仍然有效。
- **为什么这么选**：用户选择"在时限内预留"，而不是"超时后再加时"，这样总时间可预期。用已有证据交一份不完整的答案，比空答好。
- **效果**：16 道没交答案的题重跑后全部交了答案，平均 0.78，其中 10 道满分。真正"到点强制交稿"的流程，真实运行里还没触发过，目前只有离线测试验证。

### 11. 动态网页读不到

- **问题和表现**：有些 0 分题需要的数据在需要交互的网页里，比如表格要点击、筛选后才出现，读网页工具拿不到。
- **原因**：读网页工具只取静态内容。评测入口当时是关闭浏览器的。
- **方案**：评测加 `--browser` 开关，每个 Agent 各开一个独立的无界面浏览器，互不抢占；访问同样经过答案网站黑名单，事后审计浏览器访问了哪些网址。
- **为什么这么选**：浏览器是网页版已有的能力，评测开上它，才能看出它在真实题目上有多大用处，也和网页口径一致。
- **效果**：185、506、155、606 从 0 分到满分。4 路并发、开着 4 个浏览器，内存峰值约 2.5 GB。但遇到 Cloudflare 这类人机验证照样过不去（IUCN、opensecrets 等），555、805 还是 0 分。hard50 里有 16 题用了浏览器，主要是主 Agent 在用。

### 12. 小问题和运行上的坑

- **泄题检查崩溃**：`bash_leak_audit` 用 `splitlines` 分行，会被某些特殊字符切碎，导致第 35 题崩溃。改用按 `\n` 分行，并补了测试。
- **导出资料后的 bash 崩溃**：导出资料后，带 fetch 的 bash 因清单文件缺来源编号而崩溃（第 594 题），已修。
- **中转服务故障和额度**：ITKK 中途出过故障，额度也快用完。规则定为：遇到限流就降并发、不停；额度用完才停；服务故障时可以停，故障期间失败的题挪到一边，恢复后用同一批次名续跑，已完成的题自动跳过。后来研究改走 opencode，评分仍走 ITKK 的 Gemini。
- **停进程留下孤儿进程**：直接 kill 研究脚本会留下孤儿 worker。改用包装脚本：子进程放进独立进程组，停止时整组一起结束。

## 四、非满分题还剩什么问题

900 题里还有 121 道没拿满分，逐题按评分说明和答案内容归了类。依据是摘要，没有逐题翻完整轨迹，有主观成分。

| 原因 | 题数 | 0 分 | 约丢掉几题的分 |
|---|---|---|---|
| 数据来源、版本或时间点和标准答案不同（数值卡线、用了最新版数据） | 44 | 19 | 24.1 |
| 题意或口径理解不同 | 39 | 9 | 16.5 |
| 推理或识别出错 | 10 | 5 | 5.6 |
| 网站拦截，取不到数据 | 6 | 2 | 3.3 |
| 多答（边界项也列进去） | 10 | 0 | 2.6 |
| 没查全 | 6 | 1 | 1.9 |
| 格式（多写了说明） | 2 | 0 | 0.7 |
| 标准答案或评分可疑 | 4 | 0 | 0.3 |

结论：前面那些程序问题（卡死、交不出答案、误停、截断）都已经修掉。剩下的丢分大多出在交稿时的取舍：

- 答案常常在"未解决缺口"里已经写出了另一种读法的结果，那正好是标准答案，但正文选了另一种。
- 题目指定了年份，却用了最新版数据。
- 拿不准的时候，把两种答案都写进正文，结果被算成多答。

## 五、还没做的和下一步

1. **交稿前的取舍检查**（提示词或流程改动，需要做对比测试）：对照题目原文字面选读法；指定了年份就用当年的数据版本；正文只放一个答案，备选放说明里。
2. **强制交稿实测**：造一道必然超时的题，把"研究到点 → 只允许交稿"在真实运行里走一遍。
3. **浏览器开 / 关对照**：固定其他条件只切换浏览器，单独测它的贡献。
4. **全量正式重跑**：用修好的代码把 900 题重跑一遍，拿正式分数。
5. **BCP 同模型多框架对照**：证明分数来自框架而不只是模型（见 `eval/README.md` 的核心实验）。目前只有 3 题试跑，官方标准 Agent 没有时间上限，需要先补上与我们相同的 900 秒上限。
6. **人工核对可疑标准答案**：66、139、276、584。
7. **技能实际很少被加载**：10-07 的 24 题里，主、子 Agent 实际加载技能的次数都是 0；网页上做综述类题时，也只有一个子 Agent 加载了一次。现有技能主要针对查找题，开放式综述没有对应的技能。

## 六、方法上的经验

- **一次只改一处，固定题目做对照。** 只看几道题的结论，常被随机波动淹没（DRB2、BCP 的 3 题批次里，每道题都在某次运行中错过）。
- **先统一评分口径，再比分数。** 换裁判就能差 2 个点。
- **先找机制问题，再调提示词。** 卡死、截断、误停这些问题，改提示词救不回来，而且一修掉就有明显效果。
- **不给产品加需求外的限制来"修"问题。** 卡死换了更快的算法，没有加长度上限；读不到长 PDF 去掉了截断，而不是改成截得更长。
- **0 分题要逐题看原因。** 很多"答错"其实是口径分歧，答案自己已经点出来了，这和"没查到"需要不同的改法。
